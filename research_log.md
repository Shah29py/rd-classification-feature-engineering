# Case 7 — Research Log

## 1. Цель проекта

**Case 7 — Feature Engineering для классификатора товарной группы Разрешительных Документов.**

Целевые товарные группы:

- TG 4 — Парфюмерия
- TG 35 — Косметика, бытовая химия и товары личной гигиены
- TG 43 — Моторные масла

Главная задача проекта — исследовать RD dataset и найти признаки, которые позволяют определить принадлежность разрешительного документа к одной или нескольким целевым товарным группам.

После консультации с экспертом уточнено:

- основной результат проекта — **качественное исследование данных и Feature Discovery**;
- обучение модели является дополнительным этапом, если останется время;
- использовать можно и рекомендуется не только текст, но и все доступные структурированные поля JSON.

---

## 3.4 Структура JSON и повторяющиеся документы

### Что исследовали

- вложенные объекты `product`, `manufacturer`, `applicant`, `certificate`, `declaration`;
- повторяющиеся `rd_documentnumber`;
- распределение `rank`.

### Наблюдения

- один и тот же `rd_documentnumber` может встречаться несколько раз;
- ранее найдено 7714 повторяющихся `rd_documentnumber`;
- у повторяющихся записей встречаются разные значения `rank` (например 1–4);
- структура JSON неоднородна;
- вложенные объекты могут присутствовать, но содержать пустые значения.

### Важное уточнение после встречи с экспертом

`rank` **не следует интерпретировать как версию или актуальность документа**.

Эксперт объяснил, что `rank` используется для различения нескольких записей, связанных с одним разрешительным документом. Для идентификации важна совокупность номера документа и даты регистрации.

Поэтому старую гипотезу:

> `rank` = версия документа

считаем **отменённой**.

При дальнейшем join необходимо учитывать повторяющиеся записи и не удалять их механически без понимания соответствия.

## 3.5 Первичный анализ `product`

### Структура

В `product` встречались, в частности, поля:

- `tnved`
- `productInfo`
- `productName`
- `idObjectType`
- `identification`
- `idProductOrigin`

В части документов структура была сокращённой.

### `idObjectType`

Основные значения:

- `Серийный выпуск`
- `Партия`
- `Единичное изделие`

Это **candidate feature**, но пока не доказанный признак.

### `idProductOrigin`

Содержит страну происхождения товара.

Среди наиболее частых значений:

- Россия
- Китай
- Италия
- Германия
- Франция

Значительная доля значений пустая или `None`.

Это также **candidate feature**, требующий сравнения распределений по TG.

### `identification`

При просмотре первых 50 000 документов полезных непустых значений в `product.identification` не найдено.

### `product.tnved`

Ключ `tnved` встречается в структуре `product`, однако в проверенных данных часто содержал пустую строку.

Поэтому пока нельзя утверждать, что `product.tnved` является пригодным источником признака. Требуется оценить заполненность и реальные значения на всём наборе.

### Важное исправление

Ранее в журнале было записано, что `product` имеет 4467 комбинаций ключей.

Это было некорректное обобщение: число 4467 относится к наиболее частой **структуре верхнего уровня JSON**, а не к количеству структур `product`.

Корректно говорить:

> структура `product` неоднородна, но в исследованной выборке преобладает схема с шестью полями `tnved`, `productInfo`, `productName`, `idObjectType`, `identification`, `idProductOrigin`.

# 4. Блок 2 — RD ↔ Truth и анализ разметки

## 4.1 Связь RD и Truth

### Что было раньше

Первоначально прямое совпадение между `case_df.rd_documentnumber` и старым `truth_df.rd_number` практически не находилось.

После консультации эксперт:

- исправил `rd_number`;
- обновил Truth dataset;
- добавил `rd_date`.

### Проверка после обновления

Из обновлённого Truth dataset случайно выбраны 100 значений `rd_number`.

Для каждого проверялось наличие такого же номера в:

```python
case_df["rd_documentnumber"]
```

### Результат

Совпало:

**94 из 100**.

### Вывод

После исправления `rd_number` прямое соединение по номеру документа стало рабочим.

Однако 94/100 — это проверка выборки, а не точная оценка полного качества join.

Следующий шаг — выполнить полный join и измерить:

- долю совпавших Truth;
- долю unmatched Truth;
- количество RD без Truth;
- количество повторов;
- many-to-many случаи.

---

## 4.2 Повторы одного документа

Для примера один `rd_number` встречался:

- несколько раз в `case_df`;
- с разными `rank`;
- несколько раз в Truth.

В Truth повторяющиеся строки при этом могли иметь одинаковые:

- `tg`;
- `rd_type`;
- `group_tnved`;
- `code_tnved`;
- `rd_number`.

### Вывод

Нельзя автоматически считать каждую строку Truth отдельным независимым документом.

Объект классификации — **разрешительный документ**, однако внутри датасетов один документ может быть представлен несколькими строками.

Это необходимо учитывать при формировании feature dataset.

---

## 4.3 `rd_date`

После обновления Truth появилась колонка `rd_date`.

Из проведённой проверки:

- TG 4: заполнено практически 100%;
- TG 43: заполнено примерно 99.5%;
- TG 35: дата отсутствует.

В целом около 60.7% значений `rd_date` отсутствуют, в основном из-за TG 35.

### Вывод

`rd_date` может быть потенциальным признаком, но **не является универсальным**, поскольку для TG 35 дата отсутствует.

---

## 4.4 `rd_number` как содержательное поле

В старом Truth dataset `rd_number` выглядел неоднородно.

Для TG 35 и TG 43 преимущественно встречались номера документов.

Для TG 4 встречались:

- названия продукции;
- выдержки из деклараций;
- ГОСТ;
- торговые марки;
- даты;
- другие текстовые фрагменты.

После исправления `rd_number` экспертом эта проблема была частично устранена.

### Вывод

Старые результаты по "грязному `rd_number`" нужно рассматривать как **историю проблемы качества исходной версии Truth**, а не как актуальную характеристику обновлённого dataset.

---

## 4.5 `code_tnved`

### Наблюдение

Распределение кодов ТН ВЭД по целевым группам сильно различается.

#### TG 4

Практически полностью представлены двумя кодами:

- `3303009000`
- `3303001000`

#### TG 35

Используется значительно больше кодов, среди частых:

- `3304990000`
- `3305900009`
- `3402500000`
- `3304300000`
- `3401300000`
- и др.

#### TG 43

Характерны коды, связанные с маслами и смазочными материалами, например:

- `2710198200`
- `2710198800`
- `3403199000`
- `3820000000`
- `3403990000`
- и др.

Также встречаются явно невалидные/текстовые значения вроде:

- `ACEA A3`
- `VW 502.00/505.00`
- `Renault 0700`

### Вывод

`code_tnved` — **сильный кандидат в признаки**.

Перед использованием необходимо:

1. очистить значения;
2. отделить настоящие коды ТН ВЭД от текстовых значений;
3. проверить уровень обобщения кода;
4. сопоставить коды с Definitions;
5. оценить coverage и распределение по TG.

Важно: сам `code_tnved` из Truth нельзя без проверки использовать как feature для нового RD, если аналогичная информация недоступна в самом RD.

---

## 4.6 Анализ множественной принадлежности TG

Эксперт подтвердил:

- один документ может относиться к нескольким товарным группам;
- комбинация TG 4 + TG 35 возможна;
- другие комбинации считаются менее вероятными;
- `tg_ids` — автоматическая классификация организации и может содержать ошибки.

Следовательно:

- нельзя брать только первый TG из `tg_ids`;
- нужно исследовать комбинации TG;
- Truth следует использовать как основную разметку для анализа, но структуру multi-label также необходимо учитывать.

# 6. Блок 3 — Feature Discovery

Это **текущий главный блок проекта**.

Цель:

> найти характеристики разрешительного документа, которые статистически отличаются между TG 4, TG 35 и TG 43.

Исследование делим на:

### 6.1 Текстовые признаки

- `nameProd`;
- `docNorm`;
- `useArea`;
- `protocol`;
- `firmMadeName`;
- `firmGetName`;
- другие текстовые поля.

Ищем:

- ключевые слова;
- устойчивые фразы;
- паттерны;
- длины;
- единицы измерения;
- особенности терминологии.

### 6.2 Структурированные признаки

Исследовать:

- `product`;
- `manufacturer`;
- `applicant`;
- `certificate`;
- `declaration`;
- остальные вложенные объекты.

Для каждого:

1. структура;
2. заполненность;
3. частые значения;
4. распределение по TG;
5. потенциальные закономерности.

### 6.3 Производные признаки

Например:

- поле присутствует / отсутствует;
- значение пустое / непустое;
- тип объекта;
- количество элементов;
- длина текста;
- количество производителей;
- количество заявителей;
- комбинация нескольких признаков.

# 7. Правило оценки candidate feature

Найденную закономерность пока не называем "хорошей фичей".

Для каждого кандидата фиксируем:

| Поле | Что оцениваем |
|---|---|
| Feature | Что именно проверяем |
| Source | Откуда берётся |
| Coverage | На какой доле RD доступно |
| TG 4 | Частота / доля |
| TG 35 | Частота / доля |
| TG 43 | Частота / доля |
| Specificity | Насколько признак специфичен |
| Status | Candidate / Validated / Rejected |
| Notes | Ограничения и интерпретация |

Принцип:

```text
Observation
    ↓
Statistic
    ↓
Comparison by TG
    ↓
Interpretation
    ↓
Candidate feature
    ↓
Evaluation
```

# 8. Важные принципы проекта

1. Не строить модель до завершения Feature Discovery.
2. Не считать `tg_ids` идеальной разметкой.
3. Не выбрасывать документы с несколькими TG автоматически.
4. Не интерпретировать `rank` как версию документа.
5. Не исправлять весь мусор вручную без оценки его масштаба.
6. Не считать любую корреляцию полезной feature.
7. Не ограничиваться текстом — структурированный JSON является важной частью исследования.
8. Любой сильный кандидат проверять на достаточной выборке.

# 9. Следующий шаг

Перед переходом к полноценному Feature Discovery нужно закрыть минимальную часть Block 2:

1. выполнить полный join обновлённого Truth с RD;
2. оценить unmatched;
3. проверить many-to-many;
4. определить, как формировать единицу анализа "разрешительный документ";

После этого начинаем Feature Discovery с наиболее перспективных источников:

**Product → Applicant → Manufacturer → Certificate/Declaration → текстовые поля → производные признаки.**
