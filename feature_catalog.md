# Case 7 — Feature Catalog

> Этот файл содержит **кандидатные признаки**, найденные в ходе исследования.
> Признак не считается подтверждённым только потому, что он логично звучит.
> Статус `Candidate` означает, что требуется проверить coverage и распределение по TG.

---

## Статусы

- `Candidate` — потенциально полезный признак, требует проверки.
- `Validated` — статистически подтверждённая полезность.
- `Rejected` — исследован, но не показал достаточной разделяющей способности.
- `To investigate` — идея требует дополнительного исследования.

---

# 1. Product

## Feature P1 — `product_object_type`

**Статус:** Candidate

**Источник:** `rd_data → product.idObjectType`

**Тип:** категориальный

**Описание:**

Тип выпуска/объекта продукции.

Наблюдались значения:

- `Серийный выпуск`
- `Партия`
- `Единичное изделие`

**Почему интересно:**

Разные товарные группы могут иметь различное распределение по типу выпуска.

**Что проверить:**

- coverage;
- распределение каждого значения по TG 4 / 35 / 43;
- наличие значений, практически отсутствующих в одной из групп.

---

## Feature P2 — `product_origin`

**Статус:** Candidate

**Источник:** `rd_data → product.idProductOrigin`

**Тип:** категориальный

**Описание:**

Страна происхождения товара.

Среди наиболее частых значений:

- Россия
- Китай
- Италия
- Германия
- Франция

Значительная доля значений пустая или `None`.

**Почему интересно:**

Страны происхождения могут иметь разное распределение по товарным группам.

**Что проверить:**

- coverage;
- top-N стран по каждой TG;
- долю TG внутри страны;
- объединённые категории стран, если отдельных стран слишком много.

---

## Feature P3 — `product_tnved`

**Статус:** To investigate

**Источник:** `rd_data → product.tnved`

**Тип:** категориальный / текстовый код

**Описание:**

Поле потенциально содержит код ТН ВЭД.

**Текущее наблюдение:**

В проверенных данных ключ встречается, но часто содержит пустую строку.

**Почему статус не Candidate:**

Пока не установлено, что поле имеет достаточное заполнение и пригодные значения на полном RD dataset.

**Что проверить:**

- долю непустых значений;
- уникальные значения;
- валидность кодов;
- совпадение с кодами из Truth / TG Definitions;
- распределение по TG.

# 2. Text

## Feature T1 — `perfume_keyword_presence`

**Статус:** Candidate

**Источник:** RD text fields; словарь терминов сформирован с использованием `TG_Definitions.xlsx`

**Тип:** бинарный

**Описание:**

Наличие характерных парфюмерных терминов в текстовых полях RD, например:

- `духи`
- `одеколон`
- `туалетная вода`
- `парфюмерная вода`
- `perfume`
- `parfum`

**Важное ограничение:**

Первичная проверка показала, что простая проверка отдельных слов даёт мало совпадений для TG 4. Поэтому это пока только candidate feature.

**Что проверить:**

- какие текстовые поля лучше использовать;
- нормализацию русского/английского написания;
- морфологические варианты;
- coverage;
- false positives / false negatives.

---

## Feature T2 — `cosmetics_keyword_presence`

**Статус:** Candidate

**Источник:** RD text fields + `TG_Definitions.xlsx`

**Тип:** бинарный / набор бинарных признаков

**Примеры терминов:**

- крем
- шампун
- лосьон
- маска
- бальзам

**Важное наблюдение:**

Простое наличие слова `крем` может давать ложные срабатывания вне косметики. Например, оно встречалось в названиях пищевых продуктов.

Следовательно, нельзя использовать слово `крем` как доказанный самостоятельный признак.

**Что проверить:**

- контекст слова;
- сочетания слов;
- TF-IDF / n-grams;
- false positives;
- specificity.

---

## Feature T3 — `motor_oil_keyword_presence`

**Статус:** Candidate

**Источник:** RD text fields + `TG_Definitions.xlsx`

**Тип:** бинарный / набор бинарных признаков

**Примеры терминов/паттернов:**

- моторное масло
- масло моторное
- `API`
- `SAE`
- `5W`
- `10W`
- другие спецификации моторных масел.

**Важное наблюдение:**

Простая проверка отдельных терминов на небольшой выборке дала мало совпадений.

**Что проверить:**

- паттерны вида `5W-30`, `10W-40`;
- API/SAE-классификации;
- ACEA;
- допуски производителей (`VW`, `MB`, `Renault` и т.д.);
- контекст употребления.

# 3. Truth-derived candidate

## Feature C1 — `tnved_code`

**Статус:** Candidate / To investigate

**Источник:** `truth_df.code_tnved`

**Тип:** категориальный

**Описание:**

Коды ТН ВЭД сильно различаются между целевыми TG.

Наблюдения:

- TG 4 почти полностью представлена двумя кодами;
- TG 35 имеет более широкий набор кодов;
- TG 43 имеет характерный набор кодов масел и смазочных материалов.

Также встречаются загрязнённые значения:

- `ACEA A3`
- `VW 502.00/505.00`
- `Renault 0700`
- и др.

**Критическое ограничение:**

`truth_df.code_tnved` можно использовать как источник для анализа и как candidate feature только в том случае, если соответствующая информация доступна из самого RD при inference.

Нельзя просто передать `truth_df.code_tnved` модели как feature, если для нового документа такого значения нет.

**Что проверить:**

- где тот же код находится в RD;
- можно ли надёжно извлекать его из `rd_data`;
- как нормализовать коды;
- какой уровень кода наиболее информативен.

# 4. Structural candidates

## Feature S1 — `json_field_presence`

**Статус:** To investigate

**Источник:** структура `rd_data`

**Тип:** бинарные признаки

**Описание:**

Сам факт присутствия/отсутствия структурированного поля может быть информативен.

Примеры:

- `product` присутствует;
- `certificate` присутствует;
- `declaration` присутствует;
- `applicant` присутствует;
- `manufacturer` присутствует.

**Почему интересно:**

Эксперт отдельно указал, что даже тип/структура Applicant может отличать товарные группы.

**Что проверить:**

Для каждого поля:

- coverage;
- долю заполненных значений;
- распределение по TG.

---

## Feature S2 — `json_structure_pattern`

**Статус:** To investigate

**Источник:** структура JSON

**Тип:** категориальный / бинарный набор

**Описание:**

Определённые комбинации присутствующих полей могут быть характерны для отдельных типов РД.

Например:

```text
certificate present
+
declaration absent
```

или:

```text
applicant present
+
manufacturer present
+
certificate present
```

**Что проверить:**

- наиболее частые схемы;
- распределение схем по TG;
- не является ли схема просто прокси для типа документа.

# 5. Пока не добавляем как готовые features

Следующие идеи обсуждались, но ещё недостаточно исследованы:

- `has_TR_TS_009`;
- дата регистрации;
- тип документа;
- `Applicant.type`;
- конкретные значения `Applicant`;
- конкретные значения `Manufacturer`;
- наличие `Certificate`;
- наличие `Declaration`;
- длина `nameProd`;
- длина `docNorm`;
- количество производителей;
- количество заявителей;
- комбинации структурированных полей.

Они должны попасть в каталог после фактического анализа данных, а не заранее объявляться готовыми features.

# 7. Главный принцип каталога

`feature_catalog.md` — это **не список всех идей**.

Это журнал доказательств:

```text
идея
  ↓
наблюдение
  ↓
статистика
  ↓
сравнение TG
  ↓
candidate
  ↓
evaluation
  ↓
validated / rejected
```

Поэтому подтверждённые признаки должны появляться в каталоге только после Block 4 — Feature Evaluation.
